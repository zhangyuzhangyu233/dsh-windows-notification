# dsh-windows-notification — build contract (shared by all agents)

Status: v1 implementation. Read this whole file before writing code. It is the single source of truth for
file ownership, runtime contracts and verification. If reality contradicts this document, report the
contradiction to the Lead instead of silently diverging.

## Product

A DeepSeek Harness plugin that posts **native Windows toast notifications** when the harness wants the
user's attention:

- a turn finishes (`turn/end` with reason `completed`),
- a turn fails (`turn/end` with reason `error`),
- an approval is requested (`approval/request`).

Requirement from the user: the notification must **appear to come from the DeepSeek Harness desktop app
itself** (not from Windows PowerShell), and it must be **actionable like Codex's notifications** (buttons
that do something).

Facts verified on this machine:

- DSH's registered AppUserModelID is `com.deepseek.dsh` (Start Menu shortcut
  `%APPDATA%\Microsoft\Windows\Start Menu\Programs\DeepSeek Harness.lnk`, `Get-StartApps` shows it).
  Toasts created with `CreateToastNotifier('com.deepseek.dsh')` are accepted by the notification platform
  (they land in notification history under `HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Notifications\Settings\com.deepseek.dsh`)
  and are attributed to DeepSeek Harness with its icon.
- The host process is plain Node (`ELECTRON_RUN_AS_NODE`), so Electron's Notification API is NOT reachable.
  Windows PowerShell 5.1 (`C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe`) + WinRT
  `Windows.UI.Notifications` is the transport.
- The machine currently suppresses banner display (DND/focus). Do not treat "no banner on screen" as failure
  by itself: verify via WinRT toast history, the registry stamp, and (when possible) the notification center.

## Runtime architecture

```
DSH host process (plain Node, index.js)
  ├─ ctx.on('session/event')      turn/end → toast "finished" / "error"
  ├─ ctx.on('approval/request', …, { prepend: true })
  │     when the DSH window is NOT foreground and approvalActions is on:
  │       show approval toast with 允许一次 / 拒绝 / 打开 DSH buttons,
  │       await the user's click or timeout, then return the ApprovalOutcome
  │       (fall back to next() so the in-app UI asks as usual)
  ├─ local HTTP bridge 127.0.0.1:<random port> + token
  │     POST /action  {token, action:'open'|'approve'|'deny', sessionId?, approvalId?}
  │     → focuses DSH / resolves a pending approval
  ├─ child_process.spawn(powershell.exe, …) → toast.ps1 (show, check foreground)
  └─ writes %LOCALAPPDATA%\dsh-windows-notification\bridge.json for the protocol handler
Windows notification click
  → protocol dsh-notify://… (registered once under HKCU\Software\Classes\dsh-notify)
  → notify-handler.ps1 %1
      → POST to the bridge (approve / deny / open)
      → focus the DeepSeek Harness window (for open; restore if minimized)
```

### Toast identity

Every toast uses AUMID `com.deepseek.dsh`. Because that AUMID belongs to the DSH Start Menu entry, Windows
shows the notification as "DeepSeek Harness" with its icon.

Toast XML skeleton built by `index.js` (toast.ps1 only displays it):

```xml
<toast duration="long">
  <visual><binding template="ToastGeneric">
    <text>DeepSeek Harness</text>
    <text>…title / session title…</text>
    <text>…body / preview…</text>
  </binding></visual>
  <actions>
    <action content="打开 DSH" activationType="protocol" arguments="dsh-notify://open?session=…"/>
    <action content="知道了" activationType="system" arguments="dismiss"/>
  </actions>
</toast>
```

Approval toast actions:

```xml
<action content="允许一次" activationType="protocol" arguments="dsh-notify://decision?action=approve&amp;approval=…&amp;session=…"/>
<action content="拒绝"     activationType="protocol" arguments="dsh-notify://decision?action=deny&amp;approval=…&amp;session=…"/>
<action content="打开 DSH" activationType="protocol" arguments="dsh-notify://open?session=…"/>
```

(URI query values must be URI-encoded; approve/deny must carry the one-time `approvalId` generated by the
host. `toast.ps1` must not rewrite the XML.)

## Settings namespace

Namespace: `windows-notification` (lowercase hyphenated, required by the settings service).

Resolved value (all fields required in the schema):

| field | type | default | meaning |
|---|---|---|---|
| `enabled` | boolean | `true` | master switch |
| `onTurnComplete` | boolean | `true` | notify when a turn completes |
| `onApproval` | boolean | `true` | notify/handle approvals |
| `onError` | boolean | `true` | notify when a turn fails |
| `skipWhenForeground` | boolean | `true` | do not post automatic toasts while the DSH window is foreground |
| `includePreview` | boolean | `true` | include the reply text preview in the body |
| `sound` | `'default' \| 'silent'` | `'default'` | toast audio |
| `approvalActions` | boolean | `true` | claim approvals while DSH is not foreground and answer from the toast |
| `approvalTimeoutSec` | integer 5–300 | `30` | fall back to the in-app prompt after this many seconds |
| `maxPreviewChars` | integer 40–500 | `180` | preview truncation |
| `testPing` | integer (epoch ms, `0`) | `0` | write-only trigger: when the value changes the host posts a test toast |

Composition config (`cordis.patch.yml`) is the settings `base` layer. The user layer overrides it and the
Settings → Plugins card edits the user layer.

Host side (no `@deepseek-ai/*` imports are possible from a linked package — the plugin must be
dependency-free Node ESM):

- `ctx.get('settings')` → if present, `ctx.settings.installSection(ctx, 'windows-notification', schema, baseConfig, hooks)`.
  If the service is absent, fall back to the row config and keep working.
- `schema` must be a callable `(value) => resolvedValue` with `.toJSON()` returning a serialized Schemastery
  envelope (the client rehydrates and validates with it). Generate the envelope offline with the real
  Schemastery package and embed it as a JS literal; do not import it at runtime.
  - Real Schemastery lives at
    `<npm global>/@deepseek-ai/dsh/node_modules/@deepseek-ai/schemastery`

- Read current value via the `installSection` hooks source; `onChange` fires on every committed change and on
  attach/detach. React to it: update config, and when `testPing` changes post a test toast.

## PowerShell CLI contracts

Windows PowerShell 5.1 only (do not require pwsh 7). All scripts are UTF-8 files; host passes/reads UTF-8.

### toast.ps1

```
toast.ps1 -CheckOnly
  → stdout: {"ok":true,"foreground":true|false,"dshPid":<int|null>}
  foreground = the foreground window belongs to a running "DeepSeek Harness" process (any window).
  Must finish in < 2s.

toast.ps1 -XmlBase64 <utf8-xml-base64> [-Aumid com.deepseek.dsh] [-Tag <string>] [-SkipWhenForeground] [-Priority high|default]
  → stdout: {"ok":true,"shown":true|false,"reason":"foreground"|"shown"|…,"foreground":bool}
  Decode UTF-8 base64 → XmlDocument → ToastNotification → Show().
  -Priority high sets ToastNotification.Priority = High (priority notifications may break through
  Do Not Disturb when the user allows DSH as a priority app; default stays "default"; ignore failure).
  -SkipWhenForeground: run the same foreground check first and skip Show() when DSH is foreground
  (reason "foreground"); still print valid JSON.
  Always exit 0 when a JSON line was printed; print JSON on errors too ({"ok":false,"error":"…"}).
  Never write extra non-JSON lines to stdout; diagnostics go to stderr or the log file.
```

### setup-protocol.ps1

```
setup-protocol.ps1 -HandlerPath <absolute notify-handler.ps1> [-LaunchTarget <absolute DSH exe>]
  Idempotently registers HKCU\Software\Classes\dsh-notify:
    (default) value = "URL:DeepSeek Harness Notification" (or a localizable text)
    "URL Protocol" = ""
    shell\open\command = "\"C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe\" -NoLogo -NoProfile
                           -NonInteractive -ExecutionPolicy Bypass -WindowStyle Hidden -File \"<handler>\" \"%1\""
  Also stores the DSH executable launch target under HKCU\Software\Classes\dsh-notify\dshLaunchTarget
  (string) for notify-handler.ps1's "app not running" fallback.
  Prints one JSON line {"ok":true,"registered":true|false}. Does not need admin. Idempotent.
```

### notify-handler.ps1

```
notify-handler.ps1 <uri>
  uri examples: dsh-notify://open?session=<id>   dsh-notify://decision?action=approve&approval=<id>&session=<id>
  Steps:
  1. Parse the URI robustly (PowerShell receives it as $args[0]; strip quotes). Query values are URI-decoded.
  2. Read %LOCALAPPDATA%\dsh-windows-notification\bridge.json {port,token}; POST
     {"token", "action":"open"|"approve"|"deny", "sessionId", "approvalId"} to http://127.0.0.1:<port>/action
     with 2.5s timeout via Invoke-RestMethod/HttpClient. Ignore/log failures; never block > 3s.
  3. For open (and by default for decision too, unless action says otherwise): bring the DSH window forward:
     find a "DeepSeek Harness" process with a main window, ShowWindow(SW_RESTORE), SetForegroundWindow.
     If DSH is not running, start the launch target stored by setup-protocol.ps1.
  4. Append one line to %LOCALAPPDATA%\dsh-windows-notification\handler.log (bounded to ~64 KB) and exit 0.
     No dialogs, no visible console (the registered command uses -WindowStyle Hidden).
```

The bridge JSON file format is owned by the host: `{"port":<int>,"token":"<hex>","pid":<host pid>,"updatedAt":<ms>}`.
The handler must tolerate a missing/stale file. Server bind failure is not fatal to the plugin.

## Host behaviour details (index.js)

Entry shape (cordis loader row plugin, no build step):

```js
export const name = 'dsh-windows-notification'
export function apply(ctx, config) { /* … */ }
```

- Guard `process.platform !== 'win32'`: log once and return (no tools/settings registered).
- Resolve plugin dir from `import.meta.url`; PowerShell path from `%SystemRoot%`.
- Never throw out of event listeners; catch and log via `ctx.logger?.warn/error` (or console).
- Spawn PowerShell with `child_process.spawn`, `windowsHide: true`, capture stdout/stderr, timeout kill.
  Serialize toast shows (a small queue) so bursts do not spawn dozens of processes; different approvals may
  still wait concurrently on their own decisions.
- Foreground check: call toast.ps1 -CheckOnly; cache the result for ~750 ms; on any failure treat as
  "not foreground" for completion notifications (safer to notify) but "abort claiming" for approvals (do not
  claim when the check is unknown; call next()).
- `turn/end` handling:
  - reason kind `completed`: if settings.enabled && onTurnComplete → content: header "DeepSeek Harness"
    + session title (ctx.get('sessionTitle')?.get(session)) + assistant preview (last assistant message text
    from the session events you observed; truncate to maxPreviewChars; include only when includePreview).
  - reason kind `error`: if enabled && onError → body with the error message (truncated).
  - Skip subagent sessions (origin/delegationDepth). Skip when skipWhenForeground and DSH is foreground
    (pass -SkipWhenForeground to toast.ps1 for the completion/error path).
  - De-duplicate per session+turn: remember the last turn number notified.
- Approval handling (prepend listener):
  - Conditions: win32, settings.enabled && onApproval && approvalActions, bridge is listening.
  - Foreground check: if DSH is foreground OR check failed → `return next()` (in-app approval UI is the right surface).
  - Else claim: create approvalId, show toast with 允许一次/拒绝/打开 DSH buttons and a body naming the tool
    and the asker's reason; wait for the bridge decision / timeout / request abort.
    - decision `allow` → return `'allowed-once'`; decision `deny` → return `'rejected'`.
    - timeout → log and `return next()` so the browser UI asks normally.
    - `request.signal` abort → return `'cancelled'`.
  - Never answer a request whose approvalId does not match the pending map; tokens are required.
- Tool `windows_notification`: the model may post one custom toast
  (params: title, body, actions?: 'none'|'open'|'dismiss'; max ~200 chars each).
  Register it only if `ctx.tools` exists and registration does not throw; keep the definition conservative.
  Confirm the raw definition shape from `dsh-tools` types / dsh-ops before implementing.
- Bridge: `node:http` server on `127.0.0.1`, port 0 (random), 32-byte hex token, POST /action only, JSON
  body limit 4 KB, 401 on bad token, 404 otherwise. Write bridge.json atomically (tmp+rename) on listen;
  delete on dispose (`ctx.effect` teardown). Only start when win32 + enabled (or start lazily on first use).
- On `apply`, when enabled: register protocol handler once via setup-protocol.ps1 (fire and forget, log failure),
  and post a "Windows 通知已连接" toast? No — do not spam on every boot. Only post when settings enable toggles
  on or when testPing changes.

# v1.1 additions — user questions + demo notifications

The user asked for **input-submission notifications**: when the agent asks the user a question
(`user-questions/request`), the Windows toast must offer the question's **options as buttons** (and a
free-text input when there are no options), and answering from the toast must resume the agent.
The settings card must offer a **demo option** (a selectable demo kind) plus a "发送演示通知" button.

## New settings fields (schema + card + row config base)

| field | type | default | meaning |
|---|---|---|---|
| `onUserQuestion` | boolean | `true` | notify when the agent asks a question |
| `questionActions` | boolean | `true` | claim a single-select question while DSH is not foreground and answer from the toast |
| `questionTimeoutSec` | integer 10–600 | `60` | fall back to the in-app question UI after this many seconds |
| `demoKind` | `'complete' \| 'approval' \| 'question-options' \| 'question-text'` | `'question-options'` | which notification the demo button fires (this is the "演示选项") |
| `demoPing` | integer (epoch ms, `0`) | `0` | write-only trigger: when it changes the host posts the demo notification |

## New protocol URIs (host builds the XML; handler parses, never rewrites)

```
dsh-notify://question?action=option&question=<qtoken>&choice=<index>&session=<sid>&focus=0
dsh-notify://question?action=text&question=<qtoken>&session=<sid>&focus=0     (+ input id "reply")
dsh-notify://question?action=open&question=<qtoken>&session=<sid>
dsh-notify://demo?kind=question-options&choice=<index>&focus=0
dsh-notify://demo?kind=approval&decision=approve|deny&focus=0
dsh-notify://demo?kind=question-text&focus=0
```

`notify-handler.ps1` must POST the extra fields to the bridge:

```json
{"token":"…","action":"answer"|"demo"|"open"|"approve"|"deny","sessionId":"…","approvalId":"…",
 "questionId":"…","choice":"…","text":"…","kind":"…"}
```

- `action=option` → `action:"answer"` + `choice`; `action=text` → `action:"answer"` + `text`;
  for a text toast the Windows input value arrives appended to the URI (e.g. `&reply=hello`); accept
  `reply`, `text`, `input`, `answer` query names as the input value.
- `focus=0` means do not steal focus (answers/demos); `open` still focuses.
- Handler stays Windows PowerShell 5.1, one JSON line on stdout, exit 0, 2.5 s bridge budget.

## Host behaviour

`ctx.on('user-questions/request', async (request, next) => …, { prepend: true })`:

- claim only when: win32, enabled && onUserQuestion && questionActions, bridge listening,
  **exactly one question**, `multiSelect !== true`, and DSH is not foreground (foreground check unknown → do not claim);
- options present → toast with up to three option buttons + `打开 DSH`; wait for bridge `action:"answer"`
  with `choice` / bridge `"open"` / timeout / request abort;
  answer = `{ answers: [{ id: q.id, selected: [label] }] }`; open/timeout/abort → `return next()`;
- no options → toast with `<input id="reply" type="text" …/>` inside `<actions>` and a `发送` action
  (`hint-inputId="reply"`); bridge `answer` with `text` → `{ answers: [{ id: q.id, selected: [], custom: text }] }`;
  empty text / timeout / abort → `next()`;
- multi-question or multiSelect → notify-only toast (`打开 DSH`) then `next()` (never claim);
- de-duplicate by pending question token; teardown releases pending questions via `next()`.

Demo (`demoPing` change): post a demo toast per `demoKind` (sample payloads; never suppressed by the
foreground check). Approval/question demo buttons use the `dsh-notify://demo…` URIs; on the bridge
`action:"demo"` the host posts a follow-up confirmation toast (e.g. `演示成功：你选择了「方案 B」`),
proving the round trip without creating a real approval/question.

# v1.2 additions — smarter push (smart summary + session collapse + high-priority questions/errors)

The user asked "让系统消息推送来的更智能". v1.2 keeps the same event coverage and adds two
user-settable smart behaviors plus better content/priority:

## New settings fields (18 total; card + schema + row config base)

| field | type | default | meaning |
|---|---|---|---|
| `smartSummary` | boolean | `true` | completion/error body gets a smart summary line and a cleaned preview |
| `sessionCollapse` | boolean | `true` | completion/error notifications for one session replace each other instead of stacking |

## Smart summary (host, `smartSummary: true`)

Track per-session current-turn telemetry from session events (`turn/start`, `step/end`, `tool/call`,
`turn/end`): start time, step count, tool-call count, up to 3 distinct tool names.

- completed body, first line: `用时 <humanized> · <steps> 步 · <toolCalls> 次工具调用` plus
  `（<tool1>、<tool2>、…）` when tool names are known; when steps/toolCalls are 0 the parts degrade
  gracefully (`用时 42 秒`).
- then the cleaned assistant preview (when includePreview): fenced-code markers / markdown links /
  heading marks / image syntax removed, whitespace collapsed, clipped to `maxPreviewChars` at a
  word/codepoint boundary with `…`.
- error body: error code (when present) + message + the same summary line; error toasts use `-Priority high`.
- humanized duration: `<60s → "42 秒"`, `>=60s → "1 分 12 秒"`.

## Session collapse (`sessionCollapse: true`)

Completion/error toasts use a stable Tag derived from an 8-hex FNV-1a hash of the session id (`sess-<8 hex>`; session ids share a `session-` prefix, so a plain prefix slice would collide across sessions), so a
newer notification for the same session replaces the older one in Action Center/history. Approval and
question toasts stay uniquely tagged/hey are pending interactions. `sessionCollapse: false` restores the
old per-turn tags.

## Priority

Approval (as before), **questions** and **error** toasts pass `-Priority high`; completion stays default.
Demo toasts stay default/unsuppressed.

## Client card

- 通知内容 group: toggle `smartSummary`「智能摘要」and toggle `sessionCollapse`「同会话合并通知」.
- `恢复默认` now unsets the 16 configurable fields (still never testPing/demoPing).
- The card must keep working against a v1.1 host snapshot (missing fields → defaults).

# v1.3 additions — desktop runtime (0.2.x) compatibility: Config schema + config-forms settings page

Discovered live: the DeepSeek Harness **desktop app** bundles runtime 0.2.1-rc.2, whose settings model is
different from the older OSS `dsh` 0.1.x runtime the plugin was first verified against:

- Settings are **per loader-entry plugin Config forms**: `SettingsForms.schema(entry)` reads
  `entry.fiber.runtime.Config` (a real schemastery schema); entries with a volatile-object Config appear
  in `settings.describe()` keyed by **loader entry id** (our row id is `dsh-windows-notification`).

# v1.4 additions — instant settings-page control channel (`/ui`) + deterministic UI port

Problem: the settings page's 发送测试通知 / 发送演示通知 previously only wrote `testPing` / `demoPing`
into the plugin Config; the toast fired on the next plugin re-apply (config editor → loader → apply),
which is slow on the 0.2.x desktop runtime and may not happen at all when the config entry is not
configurable (duplicate row). v1.4 adds a direct localhost channel so clicks show a toast immediately.

## Routes (same `127.0.0.1` server as the token-guarded `POST /action`, which is unchanged)

| Route | Method | Purpose |
|---|---|---|
| `/ui/health` | GET | `{ok, app:'dsh-windows-notification', version, uiPort, bridgePort, enabled, config(18 fields), pendingApprovals, pendingQuestions, lastApplyAt, uptimeMs}` + CORS |
| `/ui/test` | POST | post the test confirmation toast immediately → `{ok, posted, reason}` |
| `/ui/demo` | POST | body `{kind:'complete'\|'approval'\|'question-options'\|'question-text'}`, default = config `demoKind` → `{ok, posted, reason, kind}` |
| `/ui/*` | OPTIONS | CORS preflight (GET/POST/OPTIONS, content-type) |

Guards: loopback peer only (403), `Origin` anchored allowlist
`^https?://(127.0.0.1|localhost)(:\d+)?$` (absent Origin allowed for curl), 4 KB body cap, POST-only
for actions, per-route rate limit 5/10 s (429 + `retryAfterMs`). No token is needed for `/ui/*`
(the worst it can do is post a local toast); approval/answer decisions still require the token via
`/action`.

## Deterministic UI port

Bind the server to the first free candidate, preferring (on this machine Windows reserves 49510–49609):
`49514–49522` → `49714–49722` → `48080–48088` → ephemeral `0`. The chosen port is written to
`bridge.json` as `uiPort` and returned by `/ui/health`. The browser card probes all three ranges in
parallel (250 ms per probe, 1.2 s budget) and caches the discovered port.

## Client behaviour

Both shells' 发送测试通知 / 发送演示通知 buttons: show feedback immediately → discover `/ui/health` →
POST `/ui/test` or `/ui/demo {kind}` → on 2xx do **not** write the config triggers (no re-apply, no
double toast). Any failure (discovery, blocked fetch, timeout, non-2xx) falls back to the old config
write, so older hosts keep working; a failed POST clears the cached port.

## v1.4 follow-up — desktop renderer origin (`dsh-app://app`) and no-cors fallback

The 0.2.x desktop app does **not** load its UI from `http://127.0.0.1:<port>`; the window loads the
authenticated host through the custom scheme **`dsh-app://app`** (main.js forwards only that origin).
Consequences for the `/ui` control channel:

- Browser requests from the settings page carry `Origin: dsh-app://app`. The original allowlist
  (loopback http(s) only) answered the CORS preflight with **403**, so `fetch` threw before any POST —
  clicking 发送测试通知/发送演示通知 silently fell back to the config-write path.
- `/ui/*` now accepts `^https?://(127\.0\.0\.1|localhost)(:\d+)?$` **and** any
  `^dsh-app://[A-Za-z0-9.-]+(:\d+)?$` origin (case-insensitive), echoing the received origin in
  `access-control-allow-origin` and keeping `vary: origin`. Other schemes/hosts still 403.
- `POST /ui/test` and `/ui/demo` also accept `content-type: text/plain` bodies (JSON-looking bodies are
  parsed; empty/garbage bodies fall back to defaults) so a `no-cors` simple-request beacon works even if
  CORS is unavailable. The token-guarded `POST /action` is unchanged.
- Client order for the settings buttons: readable CORS discovery + confirmed POST →
  `no-cors` discovery/beacon POST (unconfirmed feedback, no config write) → legacy config-write trigger
  (old hosts only). No duplicate toasts on success.

Live symptom reproduced before the fix: `curl -H "Origin: dsh-app://app" http://127.0.0.1:<uiPort>/ui/health`
→ 403 while the same request without `Origin` → 200. After the fix: preflight 204 + ACAO echo,
POST 200 `{ok:true,posted:true}`.
